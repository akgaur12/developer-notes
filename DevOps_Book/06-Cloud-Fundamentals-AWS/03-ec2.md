# Chapter 3 — EC2 — Elastic Compute Cloud

## Learning Objectives

By the end of this chapter you will be able to:

- Select the right EC2 instance type for a given workload
- Launch, connect to, stop, and terminate EC2 instances via the CLI
- Create and manage AMIs for reuse and golden image workflows
- Attach and mount EBS volumes to instances
- Configure security groups with least-privilege inbound rules
- Write user data scripts to bootstrap instances automatically
- Explain the difference between On-Demand, Reserved, and Spot pricing

## 3.1 What Is EC2?

**EC2 (Elastic Compute Cloud)** provides virtual machines — called *instances* — that run in the AWS cloud. Each instance gives you CPU, RAM, network bandwidth, and the option to attach persistent block storage. From the OS perspective, it behaves exactly like a physical server.

EC2 is the foundation of most AWS architectures: every application that cannot fit into a managed service (Lambda, ECS Fargate, Elastic Beanstalk) typically runs on EC2.

---

## 3.2 EC2 Instance Types

Instance type names follow the convention `<family><generation><attributes>.<size>`:

- Family: `t` (burstable), `m` (general), `c` (compute), `r` (memory), `g` (GPU), `i` (storage)
- Generation: `3`, `5`, `6`, `7` — higher is newer and usually better price/performance
- Attributes: `g` = Graviton (ARM), `i` = Intel, `n` = network-optimised
- Size: `nano`, `micro`, `small`, `medium`, `large`, `xlarge`, `2xlarge`, ...

| Family | Optimised For | Common Types | Use Cases |
|--------|--------------|-------------|-----------|
| `t` | Burstable (general) | t3.micro, t3.large | Dev/test, low-traffic web apps, free tier |
| `m` | Balanced (general) | m5.large, m6i.xlarge | Production web apps, app servers |
| `c` | Compute | c5.large, c6g.xlarge | Web servers, batch processing, encoding |
| `r` | Memory | r5.large, r6i.xlarge | Databases, Redis, in-memory analytics |
| `g` / `p` | GPU | g4dn.xlarge, p3.2xlarge | ML inference/training, rendering |
| `i` | NVMe Storage | i3.large, i4i.xlarge | High-IOPS databases (Cassandra, MongoDB) |
| `x` | High memory | x2idn.32xlarge | SAP HANA, very large in-memory workloads |

**T-series burstable instances** deserve special mention: they earn CPU credits during idle periods and spend them during bursts. A t3.micro runs at 10% baseline and can burst to 100% until credits are exhausted. This makes them extremely cost-effective for workloads with low average but occasional spike CPU demand.

## 3.3 Launching an EC2 Instance

### Via the CLI

```bash
# Launch an Amazon Linux 2 t3.micro in us-east-1
aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t3.micro \
  --key-name my-keypair \
  --security-group-ids sg-12345678 \
  --subnet-id subnet-12345678 \
  --iam-instance-profile Name=ec2-s3-read \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=my-server},{Key=Env,Value=dev}]' \
  --user-data file://init-script.sh

# Check instance state (filter by Name tag)
aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=my-server" \
  --query 'Reservations[*].Instances[*].[InstanceId,State.Name,PublicIpAddress,PrivateIpAddress]' \
  --output table
```

### Connecting via SSH

```bash
# Set correct key permissions (SSH refuses keys that are too open)
chmod 400 ~/.ssh/my-keypair.pem

# Connect as ec2-user (Amazon Linux), ubuntu (Ubuntu), or root (some others)
ssh -i ~/.ssh/my-keypair.pem ec2-user@<public-ip>

# If no public IP (instance in private subnet), use AWS Systems Manager Session Manager
aws ssm start-session --target i-1234567890abcdef0
```

### Instance lifecycle

```bash
# Stop: instance goes to stopped state, EBS volumes persist, no hourly charge (EBS still charged)
aws ec2 stop-instances --instance-ids i-1234567890abcdef0

# Start: resumes from stopped state (may get a new public IP unless Elastic IP is used)
aws ec2 start-instances --instance-ids i-1234567890abcdef0

# Reboot: OS-level restart, no downtime from billing perspective
aws ec2 reboot-instances --instance-ids i-1234567890abcdef0

# Terminate: PERMANENT — instance and root EBS volume are deleted
aws ec2 terminate-instances --instance-ids i-1234567890abcdef0
```

## 3.4 AMIs — Amazon Machine Images

An **AMI** is a snapshot of an instance's entire state — OS, installed software, configuration, and optionally data volumes. It is the template used to launch new instances.

### AMI sources

- **AWS provided**: Amazon Linux 2, Amazon Linux 2023, Ubuntu, RHEL, Windows Server
- **AWS Marketplace**: pre-built images from vendors (Bitnami stacks, security appliances, etc.)
- **Community AMIs**: shared publicly by other users (verify trustworthiness before use)
- **Custom AMIs**: images you build from your own instances — the foundation of golden image workflows

### Finding the latest Amazon Linux 2 AMI

```bash
# Get the latest Amazon Linux 2 AMI ID for us-east-1
aws ec2 describe-images \
  --owners amazon \
  --filters \
    "Name=name,Values=amzn2-ami-hvm-*-x86_64-gp2" \
    "Name=state,Values=available" \
  --query 'sort_by(Images,&CreationDate)[-1].ImageId' \
  --output text
# → ami-0c55b159cbfafe1f0
```

### Creating a custom AMI

```bash
# Snapshot a running or stopped instance into an AMI
aws ec2 create-image \
  --instance-id i-1234567890abcdef0 \
  --name "my-app-ami-$(date +%Y%m%d)" \
  --description "Production app server with nginx and app v1.4.2" \
  --no-reboot    # skip reboot for zero-downtime (may result in inconsistent filesystem state)

# Monitor creation (takes a few minutes)
aws ec2 describe-images \
  --owners self \
  --query 'Images[*].[ImageId,Name,State]' \
  --output table
```

Golden image workflow: configure a base instance → create an AMI → use that AMI for all subsequent launches. When you update software, create a new AMI version and update your Auto Scaling launch template.

## 3.5 Storage: EBS Volumes

**EBS (Elastic Block Store)** provides persistent block storage that attaches to EC2 instances like a hard drive. Data on EBS survives instance stop/start but by default the root volume is deleted on termination.

### EBS volume types

| Type | Description | IOPS | Throughput | Use Case |
|------|-------------|------|-----------|---------|
| `gp3` | General purpose SSD (default) | Up to 16,000 | Up to 1,000 MB/s | Most workloads |
| `gp2` | Older general purpose SSD | 3 IOPS/GB, up to 16,000 | 250 MB/s | Legacy workloads |
| `io2` | Provisioned IOPS SSD | Up to 64,000 | 1,000 MB/s | Databases, critical apps |
| `st1` | Throughput-optimised HDD | 500 IOPS | 500 MB/s | Big data, data warehouses |
| `sc1` | Cold HDD | 250 IOPS | 250 MB/s | Archival, infrequent access |

### Creating and attaching a volume

```bash
# Create a 20 GB gp3 volume in the same AZ as your instance
aws ec2 create-volume \
  --size 20 \
  --volume-type gp3 \
  --availability-zone us-east-1a \
  --tag-specifications 'ResourceType=volume,Tags=[{Key=Name,Value=data-disk}]'

# Attach to the instance (device name varies; /dev/sdf through /dev/sdp are common)
aws ec2 attach-volume \
  --volume-id vol-1234567890abcdef0 \
  --instance-id i-1234567890abcdef0 \
  --device /dev/sdf
```

### Mounting the volume on the instance

```bash
# SSH into the instance, then:

# Check that the device is visible
lsblk
# → sdf    8:80   0  20G  0 disk

# Format the volume (first time only — this destroys any existing data)
sudo mkfs.ext4 /dev/sdf

# Create a mount point and mount
sudo mkdir -p /data
sudo mount /dev/sdf /data

# Make permanent across reboots by adding to /etc/fstab
echo '/dev/sdf /data ext4 defaults,nofail 0 2' | sudo tee -a /etc/fstab
```

### EBS snapshots

```bash
# Take a point-in-time snapshot of a volume (stored in S3, billed per GB)
aws ec2 create-snapshot \
  --volume-id vol-1234567890abcdef0 \
  --description "Pre-upgrade snapshot $(date +%Y%m%d)"

# Restore: create a new volume from a snapshot
aws ec2 create-volume \
  --snapshot-id snap-1234567890abcdef0 \
  --availability-zone us-east-1a \
  --volume-type gp3
```

## 3.6 Security Groups

A **security group** is a stateful virtual firewall that controls traffic to and from EC2 instances. *Stateful* means return traffic for allowed connections is automatically permitted — you do not need separate outbound rules for responses.

Rules you set:
- **Inbound**: what traffic can reach the instance (default: deny all)
- **Outbound**: what traffic can leave the instance (default: allow all)

```bash
# Create a security group in a VPC
aws ec2 create-security-group \
  --group-name web-servers \
  --description "HTTP/HTTPS from anywhere, SSH from my IP only" \
  --vpc-id vpc-12345678

# Allow HTTP from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id sg-12345678 \
  --protocol tcp --port 80 --cidr 0.0.0.0/0

# Allow HTTPS from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id sg-12345678 \
  --protocol tcp --port 443 --cidr 0.0.0.0/0

# Allow SSH from your IP only (never open SSH to 0.0.0.0/0 in production)
aws ec2 authorize-security-group-ingress \
  --group-id sg-12345678 \
  --protocol tcp --port 22 \
  --cidr $(curl -s https://ifconfig.me)/32

# Verify rules
aws ec2 describe-security-groups --group-ids sg-12345678
```

### Security group best practices

- Deny all inbound by default — only open ports your application needs.
- Restrict SSH/RDP to specific IP ranges or use AWS Systems Manager Session Manager instead of SSH.
- Reference security groups by ID in rules rather than CIDR when possible (e.g., allow traffic from the load balancer security group to the app server security group).
- Never use `0.0.0.0/0` for SSH or database ports in production.

## 3.7 User Data — Bootstrap Scripts

**User data** is a script passed to an EC2 instance at launch time. It runs as root on the first boot, before any user logs in. Use it to install software, configure services, and deploy your application automatically.

```bash
#!/bin/bash
# user-data.sh — install Docker and run the application container

# Update the OS
yum update -y

# Install Docker
yum install -y docker
systemctl start docker
systemctl enable docker

# Allow ec2-user to run Docker without sudo
usermod -aG docker ec2-user

# Pull and start the application
docker pull ghcr.io/myorg/myapp:latest
docker run -d \
  --name myapp \
  --restart=unless-stopped \
  -p 80:3000 \
  -e DB_HOST="${DB_HOST}" \
  ghcr.io/myorg/myapp:latest

# Signal success to CloudFormation/EC2 (optional)
/opt/aws/bin/cfn-signal -e $? || true
```

Pass the script at launch:

```bash
aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t3.micro \
  --user-data file://user-data.sh \
  ...
```

View user data execution logs on the instance:

```bash
# Amazon Linux 2
sudo cat /var/log/cloud-init-output.log
```

## 3.8 EC2 Instance Metadata Service (IMDS)

The **metadata service** is a special endpoint available only from inside an EC2 instance at `169.254.169.254`. It provides instance-specific information without requiring any credentials.

```bash
# From inside an EC2 instance — no credentials needed
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Get instance ID
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id

# Get instance type
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-type

# Get public IP
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4

# Get AZ
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone

# Get temporary role credentials (if instance has an IAM role)
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-s3-read
```

The `-H "X-aws-ec2-metadata-token"` header is required by IMDSv2, the newer and more secure version. Always use IMDSv2; disable IMDSv1 in new accounts.

## 3.9 Pricing: On-Demand vs Reserved vs Spot

Understanding EC2 pricing is essential for cost-effective architecture.

### Approximate prices (t3.medium, us-east-1, 2024)

```
On-Demand:     $0.0416/hour  — no commitment, billed per second
Reserved (1yr): $0.0256/hour  — 38% saving over On-Demand
Reserved (3yr): $0.0162/hour  — 61% saving over On-Demand
Spot:           ~$0.0125/hour  — ~70% saving, but can be interrupted with 2-min notice
```

### Spot instance best practices

Spot instances are the cheapest option by far, but AWS can reclaim them with a 2-minute warning when capacity is needed elsewhere. Handle this gracefully:

- Use Spot for: CI/CD runners, batch jobs, stateless web tier behind a load balancer, ML training jobs
- Never use Spot for: databases, stateful services, anything that cannot tolerate sudden termination
- Handle the interruption notice: poll `http://169.254.169.254/latest/meta-data/spot/termination-time` from your application, or catch the `EC2 Spot Instance Interruption` EventBridge event
- Use Spot with Auto Scaling Groups and diversify across multiple instance types and AZs

### Savings Plans

Savings Plans offer 40–66% discounts in exchange for committing to a minimum spend ($/hour) for 1 or 3 years. Unlike Reserved Instances, Savings Plans are flexible — they apply automatically to any EC2 instance regardless of type, size, OS, or region (Compute Savings Plans).

## Summary

- EC2 provides virtual machines in the cloud — the workhorse of AWS compute.
- Choose instance types by workload: t-series for variable/bursty, c-series for CPU-bound, r-series for memory-bound.
- AMIs are instance snapshots used as launch templates; custom AMIs are the foundation of golden image pipelines.
- EBS provides persistent block storage; gp3 is the default and best-value option for most workloads.
- Security groups are stateful firewalls; follow least-privilege rules and never open SSH to the world.
- User data scripts automate instance bootstrap — no manual post-launch configuration needed.
- Spot instances save up to 90% but require interrupt-aware application design.
